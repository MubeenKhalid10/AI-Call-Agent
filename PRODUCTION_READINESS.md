# Production readiness — Ai-Voice-Agent

**Status on 2026-09-08: NOT declared production-ready.** Every automated
check passes (22 check scripts, the end-to-end suite over a real PostgreSQL,
the health probes, the security posture), but the requirements that can only
be proven on a real line, a real vendor account and a real network have not
been. They are listed in [§15](#15-still-requiring-manual-verification) with
the exact command for each. The go-live checklist in [§16](#16-go-live-checklist)
ends with those items; the system is production-ready when every line of it
is ticked by a person, not before.

The evidence this document rests on is regenerated by `uv run validate.py`
(`server/validation-report.md`); a reader should trust that report's date
over this file's.

**The two things that block a first real call today, on this machine:**

1. **The bot cannot speak as configured.** `server/.env` sets `TTS_PROVIDER`
   three times; the last line wins (`elevenlabs`), and the ElevenLabs key is
   rejected (HTTP 401). The Cartesia key on the same file is accepted. Fix:
   keep one `TTS_PROVIDER` line — `cartesia` with the key that works, or a
   valid ElevenLabs key — then `uv run health.py tts` must say `OK`.
   `uv run security.py check` now warns about every duplicated variable.
2. **No phone call has ever been answered on this system.** Every telephony
   path is verified against a simulated carrier and against the vendors'
   documented request shapes. The first real call is
   `uv run validate.py live --to <your phone> --dial --yes`.

## 1. Architecture overview

```
                 prospects, campaigns, the queue, results, callbacks, meetings,
                 transfers, the webhook ledger, crm_sync, the outbox, the audit
                 log, the do-not-call list, workers, pacing   ── PostgreSQL ──
                                    ▲            ▲            ▲            ▲
   ┌─────────────┐  reserves, dials │            │            │            │
   │ campaign.py │──────────────────┘   ┌────────┴───────┐    │   ┌────────┴────────┐
   │   run       │  (any number of)     │    bot.py      │    │   │  automation.py  │
   │ scheduler   │───► carrier ────────►│  Pipecat       │    │   │  n8n API + outbox│
   └─────────────┘  Twilio/SignalWire   │  STT→KB→LLM→TTS│    │   └────────┬────────┘
         ▲            (media stream)    │  tools, sink   │    │            │ signed POST
         │ status webhooks              └────────────────┘    │            ▼
   ┌─────┴───────┐                                            │          n8n
   │ webhooks.py │ (or the bot's own route)         ┌─────────┴────────┐
   └─────────────┘                                  │ campaign.py      │──► HubSpot
                                                    │   crm-sync       │
   dashboard.py (read-only, login)                  └──────────────────┘
   /healthz /readyz /metrics on every process; one trace id per call on every log line
```

- **The bot** (`bot.py`, port 7860) answers the carrier's media stream and
  holds the conversation: Deepgram Flux (STT and end-of-turn) → pgvector
  retrieval → the sales state machine and its twelve tools → Groq → TTS.
  One session per call; the call's record, result, usage and cost are written
  at teardown through a Protocol, never by importing the campaign tables.
- **The scheduler** (`campaign.py run`) reserves prospects under an advisory
  lock, gates each dial (do-not-call list, calling hours, ceilings,
  compliance policy), asks the carrier once, follows the call to its end,
  places due callbacks first, recovers what a crash left, and adopts a dead
  worker's calls. Any number of processes share one queue through PostgreSQL.
- **The webhook receiver** (the bot's route, or `webhooks.py` on 7880)
  verifies the carrier's signature against the configured public URL and
  applies each event once through a ledger.
- **The CRM syncer** (`campaign.py crm-sync`) files every finished result as a
  HubSpot contact plus a call activity, idempotently, with backoff.
- **The automation API and outbox** (`automation.py`, 7890) let n8n create
  prospects and campaigns, queue calls as callback rows, and receive signed
  `call.completed`, `lead.qualified`, `meeting.booked`, `callback.scheduled`,
  `campaign.completed` events.
- **The dashboard** (`dashboard.py`, 7870) is a read-only page and JSON behind
  a login with three roles.
- **Monitoring**: every process serves `/healthz`, `/readyz`, `/metrics`; the
  scheduler on 7895. One sixteen-hex `trace` follows a call from the dialer
  through the bot, the store, the receiver, the syncer and the deliverer.

Design rules the whole system follows: never claim what the backend did not
confirm; unknown is a value, never inferred; never two calls to one person;
the scheduler decides only *when to ask*; an unverified event touches
nothing; the CRM and n8n are reached from the rows by separate processes,
never from the call.

## 3. Deployment requirements

- **Python 3.12**, `uv`; `uv sync` in `server/` installs Pipecat 1.8.1 and
  everything else (`server/pyproject.toml`). The embedding model
  (bge-small, ~65 MB) downloads on first use into `EMBEDDING_CACHE_DIR`.
- **Five long-running processes**, each its own service unit, all reading
  the same `server/.env` and the same PostgreSQL:

  | Process | Command | Port | Liveness / readiness |
  |---|---|---|---|
  | the bot | `uv run bot.py` | 7860 (`/ws`, `/client`, the webhook path) | `/healthz`, `/readyz` |
  | the scheduler | `uv run campaign.py run` (one or more) | 7895 (`MONITORING_PORT`) | `/healthz`, `/readyz` |
  | the CRM syncer | `uv run campaign.py crm-sync` | — | its log; `crm-status` |
  | the automation API + outbox | `uv run automation.py` | 7890 | `/healthz`, `/readyz` |
  | the dashboard | `uv run dashboard.py` | 7870 | `/healthz`, `/readyz` |
  | (optional) the standalone receiver | `uv run webhooks.py` | 7880 | `/healthz`, `/readyz` |

  Restart on `/healthz` failing; route traffic on `/readyz` (503 while the
  database is unreachable or the process is draining).
- **One public HTTPS address** reaching the bot's `/ws` and the webhook path
  (`TELEPHONY_PUBLIC_URL`): the carrier streams audio to it and posts status
  events to it. ngrok for development; a real domain behind a TLS proxy in
  production. Nothing else needs to be public.
- **A TLS-terminating reverse proxy** (Caddy or nginx; snippets in
  `SECURITY.md` §4) in front of every HTTP port that leaves the machine, with
  `SECURITY_REQUIRE_HTTPS=true` and the proxy in `SECURITY_TRUSTED_PROXIES`.
  Every server binds loopback by default.
- **Outbound network access** to Deepgram, the LLM provider, the TTS
  provider, the carrier's API, Cal.com, HubSpot and n8n.
- **CPU, no GPU.** One call is one asyncio pipeline; the shared connection
  pool holds three connections per call. Memory is dominated by the
  embedding model; the eval harness's local speech models are development
  only.
- **Clocks in sync** across hosts running the scheduler: worker staleness is
  judged by the database's clock, but calling hours by the process's.
- **Windows and Linux** both run it (developed on Windows 11; the check
  scripts assume `PYTHONIOENCODING=utf-8` when redirected).

## 5. Database requirements

- **PostgreSQL 15+** with the **pgvector** extension (`CREATE EXTENSION vector`
  once as a superuser; developed against PostgreSQL 18). One database serves
  both the knowledge base and the campaign tables by default (`DATABASE_URL`
  falls back to `KB_DATABASE_URL`); they may be split.
- **Schema**: `uv run ingest.py init` (knowledge base: documents and chunks
  with a vector index) and `uv run campaign.py init` (idempotent; run it again
  after every upgrade). The campaign tables: `prospects`, `campaigns`,
  `campaign_prospects`, `call_attempts` (with `conversation_data`, `usage`,
  `cost_usd`, `idempotency_key`, `placement_started_at`, `worker_id`,
  `trace_id`), `callbacks`, `meetings` (an exclusion constraint on overlapping
  slots), `call_results`, `telephony_webhook_events` (unique `event_key`),
  `crm_sync`, `call_transfers`, `automation_events` (unique `event_key`),
  `api_requests`, `audit_log`, `dnc_numbers`, `scheduler_workers`,
  `scheduler_state`.
- **Connections**: three per live call in the bot, a pool of 4 per scheduler
  and receiver, 8 for the dashboard; PostgreSQL's default 100 caps the fleet
  at roughly twenty concurrent calls plus the servers.
- **Correctness lives here**: the reservation runs under a transaction-level
  advisory lock with `FOR UPDATE SKIP LOCKED`, a unique idempotency key and a
  live-attempt exclusion, so no prospect is ever reserved twice however many
  workers run. No Redis, no broker, no lock service.
- **Indexes**: only the ones shipped. Phase 11 measured six plausible extra
  indexes and every one made the dashboard slower; do not add them without
  measuring (`scripts/benchmark_db.py`).
- **Backups**: the rows are the only record of every call, result, consent
  and audit entry; back up on the schedule your retention policy requires.
  Transcripts are in `call_attempts.conversation_data` and `call_results`.
- **Retention**: nothing is deleted automatically; `campaign.py workers
  --prune` removes stopped worker rows only.

## 6. Webhook configuration

- **Inbound (carrier → this system).** Set `TELEPHONY_PUBLIC_URL` to the
  public HTTPS address; the receiver is mounted on the bot's server at
  `TELEPHONY_WEBHOOK_PATH` (default `/webhooks/telephony`) or served by
  `uv run webhooks.py` with `TELEPHONY_WEBHOOK_RECEIVER=standalone`. Every
  call is placed with that URL as its status callback, so nothing needs to be
  configured on the carrier's console for outbound calls. Signatures are
  verified against the *configured* URL, never the URL seen behind the proxy:
  Twilio with `TWILIO_AUTH_TOKEN`, SignalWire with `SIGNALWIRE_SIGNING_KEY`
  (from the space's API credentials page). Without the key, calls are placed
  without a callback and the worker polls instead — nothing is lost, only
  latency. A transfer's `<Dial action>` reports to the same route.
- **Outbound (this system → n8n).** `AUTOMATION_WEBHOOK_URL` (or one per
  kind), `AUTOMATION_WEBHOOK_SECRET` for `X-Aiva-Signature` (HMAC-SHA256 over
  `"<t>." + body`, five-minute tolerance) and `AUTOMATION_WEBHOOK_AUTH_HEADER/
  TOKEN` for n8n's Header Auth. Set `AUTOMATION_EVENTS_SINCE` before the first
  pass on a database with history, or every result ever written is delivered.
- **First real delivery**: place one call, then `uv run campaign.py webhooks`
  shows the ledger (`initiated`, `ringing`, `in-progress`, `completed`);
  nothing there means the carrier could not reach the URL; `webhook.refused`
  in the bot's log means the wrong signing key.

## 7. CRM configuration

`CRM_PROVIDER=hubspot`, `HUBSPOT_ACCESS_TOKEN` from a private app with the
scopes `health.py crm` names, then `uv run health.py crm` (reads one contact)
and `uv run campaign.py crm-sync --once` followed by `crm-status`. The first
pass creates the `ai_*` contact properties (`ensure_schema`) and files every
existing result — mark old drill rows `SKIPPED` first if they should not reach
the portal. Each finished call becomes a contact (matched by phone, then
email) plus a call activity carrying outcome, qualification, pain points,
objections, summary, meeting, next action and callback; writes are made once
and a lost answer is looked up by key on the next pass (`CRM_SYNC_RETRY_SECS`
should stay ≥ 60 for HubSpot's search index). Failures back off and close
after `CRM_SYNC_MAX_ATTEMPTS`; `campaign.py crm-retry` reopens them. Nothing
runs unless `campaign.py crm-sync` is running.

## 8. Calendar configuration

`CALENDAR_PROVIDER=local` needs no account: slots on a grid inside
`CALENDAR_BUSINESS_HOURS/DAYS` in `CALENDAR_TIMEZONE`, excluding what the
`meetings` table holds, with an exclusion constraint so two bots cannot book
one slot. `CALENDAR_PROVIDER=calcom` needs `CALCOM_API_KEY`,
`CALCOM_EVENT_TYPE_ID` and a `CALENDAR_SLOT_MINUTES` matching the event type
(`health.py calendar` reads it back and flags a mismatch); a lost answer is
looked up before a second booking is made. The agent never says a meeting is
booked unless the provider confirmed it and the row was written.

## 9. n8n configuration

`n8n/README.md` is the reference: the API (`/api/v1`, bearer keys per role,
`Idempotency-Key` replay), the six event kinds and their payloads (the call's
`trace_id` is on every one), the signature check as a Code node, and six
importable workflows in `n8n/workflows/` (lead intake → campaign; campaign →
calls; completed call → CRM; qualified lead → notification; meeting booked →
CRM; callback due → call). Give n8n an **operator** key
(`uv run security.py make-key --role operator`), keep admin keys with people.
The API never dials: a `POST /calls` is a callback row the scheduler places
on its next tick. First live test: import workflow 04, select its two Header
Auth credentials, activate it, `uv run automation.py --once`, `uv run
campaign.py events` — a 404 in `last_error` means the Production URL was not
used.

## 13. Known limitations

- **Nothing has been proven on a real phone line.** See §15. The audio path is verified through the eval harness (synthesised speech, local models) and a simulated carrier that speaks the media-stream protocol.
- **Groq's free tier cannot keep up with a twelve-tool agent**: throttled turns take 9–21 s to first token (`turn.late_response` in the log). A paid tier, another `LLM_PROVIDER`, or fewer tools is a decision to make before go-live.
- **The greeting takes 4–7 s** after the call connects (two vendor websockets, model loads, one inference); up to 13 s when throttled.
- **Latency figures are from the eval harness, not a live call**: p50 total 1.3 s, turn-end 0.65 s, LLM first token 0.37 s, TTS 0.15 s (HANDOFF.md §10). A real line, handset and network have not been measured.
- **The concurrency limit is one number for the fleet**, and a busy worker may hold all of it; no fair sharing, no automatic scaling.
- **Rate limits are per process**; the scheduler's metrics port is one per machine.
- **`WORKER_STALE_SECS` (60 s) is a judgement**: a database stall longer than that makes a live worker's calls adopted and then handed back.
- **TTS characters are not measured on Deepgram's websocket TTS** (Pipecat 1.8.1), so cost totals on that path name `tts` as unmeasured.
- **Inbound calls** are answered as anonymous; no number lookup is done for them, and a do-not-call heard on an anonymous call is honoured but not stored.
- **`VOICEMAIL_ACTION=message` does not hear the beep**; it waits a fixed delay after the greeting.
- **Search on the dashboard is a scan** (fine at thousands of rows, unmeasured at a million).
- **A callback's n8n event is only made while the callback is pending**; a deliverer that is not running when the callback is placed never sends `callback.scheduled` for it.
- **No multi-factor authentication, no session revocation list, no per-campaign grants** on the dashboard.
- **Counters reset per process**; the rows are the durable record.
